DREAMARI — RESEARCH THE CAREER’S WORK SURFACES

Inputs: {CAREER}, {ENTRY_ROLE}, {SETTING}, {LEVEL_OBJECTIVES}, {SCRIPT_OR_DRAFT}, {EXISTING_COMPONENT_CATALOGUE}.
The AI does the research and builds the playable result. Human intervention is QA.

1. Browse primary sources for this career’s actual work: official software documentation, professional bodies, public institutional forms and manufacturer operating guides. Collect direct source links and titles. Research the task before choosing its visual medium. Never fill a missing fact with confident-looking fake data.
2. Identify the evidence an entry-level worker actually sees or produces: a notepad, report, project file, record register, message, phone/radio conversation, software screen, prototype, plan or relevant device readout. Explain what the player reads, changes or decides. Do not copy the previous career’s objects or question sequence.
3. For each candidate, save: source; task; visual medium; necessary fields/units; normal/unknown/pending/held states; role/authority; supported actions; interpretation limits; relation to a specific script beat. Separate verified workflow facts from explicitly fictional training values and locally authored dialogue. No invented clinical/technical limits or false live readings.
4. Choose only surfaces that support the lesson or decision. Reject decorative SVG equipment, tool silhouettes, food/sample drawings, generic dashboards and arbitrary waveforms. The Nursing ECG demonstrates useful monitoring UI; its trace and readings do not belong in other careers. Messages/devices appear only where the script requires them. Do not invent unread counts, urgency, sender authority or completed actions.
5. Specify readable native HTML/CSS UI. Use small standard icons only for navigation/status. Charts must encode canonical data with labels, units and denominator; no fabricated series. Use illustration only when the player genuinely needs pictorial evidence, under the scene-art standard. Never rely on generated raster text for an answer.
6. Save a per-beat work-surface plan. Include: beat ID; learning/decision purpose; source references; evidence fields and canonical data path; current story state; selected shared mechanic; visual hierarchy; phone layout; keyboard/touch operation; selected/locked/feedback states; local-demo boundaries; reduced-motion behaviour; why no graphic if none is useful. Do not assign a graphic quota.
7. Produce artifact specifications using artifact-master-prompt.txt. Shared mechanics keep scoring and recovery; medium/content defines the profession. Evidence inside an answer control must not reveal correctness. Avoid duplicated text. Small local controls never masquerade as the game’s Continue/Submit.
8. Verify source-to-task fit, data consistency, truthful pending/live state, readable desktop/phone UI, keyboard access, unchanged scoring and progression, and one unrelated career fixture for each new shared representation. Compare task screenshots against another career: identifiable work, not just a new accent colour. Save actual test evidence and open QA limits.
9. Verify the whole art-entry chain: welcome, Play tile, trailer, lesson images, story scenes, portraits and outcomes all use the selected cast/version. Use a canonical cover reference. Inspect actual browser image sources and screenshots for both entry and gameplay. A current scene manifest does not prove the welcome image is current.

Deliver: work-graphics-research.json with sources/findings/limitations; work-surface-plan.json; artifact specifications; implemented playable surfaces; desktop/phone screenshots; test results and open QA. Never call source-backed planning or structural tests human approval or universal career validation.
