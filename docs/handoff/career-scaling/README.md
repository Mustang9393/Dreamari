# Dreamari career game production SOP

Version 1.3 · 20 October 2026 · AI production workflow; UX Designer QA draft.

**Outcome:** turn a career name (and an optional source brief) into a playable, reviewable simulation using the existing IB, nursing and aviation engine. The reusable unit is a decision with evidence, choices and consequences. A new career supplies data and art; it does not get a new gameplay implementation.

This is the entry point for **new career simulation production**. It updates the older Play SOP for complete scene images and distinguishes current shared rules from demo-specific choices. Existing approved games are not rewritten. The glossary has its own SOP and is a different product.

Files in this folder:

- `game-build-prompt.txt`: paste-ready prompt to execute this workflow.
- `art-master-prompt.txt`: complete-scene generation/edit prompt.
- `artifact-master-prompt.txt`: career-relevant work graphics, canonical data and reusable rendering contract.
- `examples/ui-ux-designer-trace.json`: teach/test dependencies from the working proof.
- `examples/ux-designer-plan.md`: brief, cast, scene geography, future levels and sources.
- `examples/ux-validation.json`: machine checks, regenerated by the validator.
- `examples/ux-pixel-test.json`: measured result of a restricted-expression edit.

## 0. AI owns production; humans QA the playable result

The only required creative input is the career name. This SOP is an instruction to the AI to research, author, design, generate assets, implement, test and repair the requested game from scratch. Human involvement is QA of a concrete playable build. Do not ask a human to write the scene list, script, questions, graphic briefs, cast, answer keys or prompts, or approve each intermediate asset.

- Infer sensible audience, setting and project defaults, and record them in the brief. Read supplied assets/scripts when present; otherwise create the missing inputs. Use the current shared engine and reference games as evidence, not a demand for a new human brief.
- The AI selects its canonical designs after checking candidates against the drawing references. In this document, “approved” or “canonical” means the selected, versioned production reference; it does not imply a human approved it. Record actual human QA separately.
- Research professional facts, cross-check the keys, inspect generated images, play the game, repair failures and repeat affected checks before handing it over. When a fact cannot be verified, choose a supported alternative task or remove the unsupported claim. Never invent a rule or label an unresolved issue passed.
- Hand over one playable QA candidate with the QA checklist, known defects and exact routes. Human QA covers authenticity, learning value, usability, art/identity continuity and taste. Provide routes/beat IDs and ask QA to report what they saw, what they expected and its severity; the AI handles the diagnosis and repair. The AI turns that feedback into fixes and regression checks; the human need not produce replacement content.
- Build the requested scope completely. If only a career is named, default to a complete Level 1 with a clearly unbuilt later-level plan. If a full multi-level game is requested, author, implement and test every requested level. A ladder or plan does not count as built content.
- Publication follows the user's existing destination authorization. Do not interrupt production for routine implementation choices; report a concrete external access or required-authorization blocker only when it actually prevents completion.

## 1. What we inherit from the three reference games

| Reference | Reusable pattern | Keep career-specific |
|---|---|---|
| Investment Banking | Mentor explains work; evidence precedes a recommendation; reviewer challenges weak reasoning; feedback explains the selected answer; reputation, review and recovery | Client documents, numerical claims, hiring odds, financial incentives, company lore |
| Registered Nurse | Choose what needs attention first; distinguish observation from interpretation; communicate a change; hand over relevant information | Clinical thresholds, protocols, doses, ECG instruments, patient-specific decisions |
| Aviation Maintenance | Check a standard before sign-off; investigate a discrepancy; keep records; stop and escalate uncertainty | Aircraft parts, torque limits, custom wrench control, illustrated toolbox/hotspots |

Transfer the reasoning pattern, not the nouns alone. A designer investigates usability; a cook checks preparation and timing; an electrician verifies an installation; a musician rehearses and responds to a brief. Do not give every career a boardroom, hospital emergency or maintenance sign-off.

## 2. Source hierarchy and scope

Read `AGENTS.md`, `docs/HANDOFF_INDEX.md`, the current `types.ts`, `scoring.ts`, `interactions.tsx` and `coreKit.ts` before building. The implementation governs runtime behaviour; old prose about scoring or timing does not override it. Chapter 11 of the Play SOP is the detailed component reference.

1. Follow the user's current instructions and supplied approved script.
2. Preserve approved story, answer keys and gameplay unless a change is requested. A source error becomes a named issue, not an invisible rewrite.
3. When no script exists, author an **AI draft**, record assumptions and sources, and identify it as such. Do not call it Joshua's script or professionally approved.
4. Verify professional facts using primary sources. Record the jurisdiction and version when relevant. Leave unsupported salary, licensing, scarcity or hiring statistics out. Fictional employers, project data and dialogue are fine when marked fictional in author notes.
5. Do not invent clinical procedures, legal advice or engineering limits to make a question work. Teach observation, checking and escalation while required specifics are missing.
6. Default delivery: one complete playable Level 1 plus a clearly unbuilt later-level plan. Build further levels when requested. Do not create empty levels that look playable or claim a full career is complete because its ladder exists.
7. A career does not need six job promotions. Where promotion titles are not meaningful, use truthful learning stages or projects, labelled as stages. An employment ladder is not a universal competency ladder.

## 3. Career brief: fill this before writing questions

Required fields:

```text
career/catalogue ID; title; career world; fictional employer or setting
source script or AI-draft status; sources; human QA status (pending until performed)
player role and authority; one concrete assignment; who uses the work
what successful work looks like; realistic consequences of poor work
mentor; reviewer; optional peer/client/participant; permanent cast designs
level outcomes (3–5); required concepts; ten scored decisions
later-level plan; source gaps; assumptions; built vs planned levels
```

Choose work a 13–14-year-old can reason through after teaching. Avoid credential trivia and unsourced numerical calculations. Keep the person in a junior role inside their authority. A good first assignment has a visible deliverable and a check: a tested flow, a documented inspection, a clear handover, a prepared service or an evidence-based recommendation.

**Gate:** each decision has a real work purpose, a teachable reason for its key, and an observable result. If you cannot explain why the better option is better, rewrite the situation before choosing a component.

## 4. Reusable interaction catalogue

All items below already exist. Use only those needed by the assignment; the reference is `11-core-kit-and-interactions.md` plus current types and scoring. Do not force all types into every level.

| Thinking required | Engine data / interaction | Authoring contract |
|---|---|---|
| Follow a story, meet a colleague, see an example | `card` | One short point and one clear CTA. Character, narrator and system voices remain distinct. |
| Learn terms | `flips`; `focus` for exactly two terms | Plain definitions, only terms later used. |
| Explore evidence or a short list | `reveal` | Each reveal adds useful information. No hidden correct-answer trick. |
| Check understanding safely | `check`, tap/type/drag | Exactly one correct answer; unlimited practice; no score or strikes. Type only when recall is the goal. |
| Make one decision | `choice`, options | One Best; each alternative has its own explanation. |
| Complete a statement | `choice`, blank/tiles | Exactly one `___`; do not test grammar instead of work reasoning. |
| Read a short artifact or reply | `choice`, document/chat | Native selectable text, not a generated image of text. Name the artifact/recipient. |
| Match concepts and purpose | `match` | Unique pairs, distinct meanings, no accidental synonyms. |
| Separate categories | `bucket` | Exactly two groups, one unambiguous destination per item; irregular authored order. |
| Order dependent work steps | `rank` | A defensible sequence, not arbitrary preference. Avoid partial credit until its current rule is deliberately chosen. |
| Find problems | `flags` | True and false rows, explicit reason for each. Do not mark mere preferences as errors. |
| Select a bounded set | `pick` | Exactly N `pick` items. Use `harmful` only for a defensible serious consequence. |
| Build an explanation | `chain` | One coherent argument in three steps; one correct option per step. Whole chain is one decision. |
| Choose a level on an ordered scale | `slider` | Four meaningful ordered labels, one Best; no timer because the engine does not enforce one here. |
| Apply several related checks | `rapid` | One scored block, clear per-item answers. Timer optional, never required merely for variety. |
| Close a level | `review` | Last beat, followed by the shared outcome flow. |

`choice` can also use the existing boss layout if an actual reviewer challenge warrants it. It is not a new question type. Avoid `inspect`, `torque`, `world`, `board`, `briefing`, `artFrame`, career-specific document styling, radio instruments, hand-placed hotspots and custom zone/move layouts in new careers. `bespokeIn(level)` must return an empty list. Never build a custom instrument just to illustrate a fact that a normal card can state. Career-specific graphic content is allowed and required where it supports the work; use the reusable artifact workflow below. A new graphic is not a new scoring mechanic.

### Choosing a question

Start with the work, then select the interaction:

- Is there one next action? Choice.
- Must the player distinguish evidence from guesses? Bucket.
- Does order matter causally? Rank.
- Are there several independent defects? Flags.
- Does a handover need a fixed set of information? Pick.
- Must a recommendation connect problem, evidence and action? Chain.

A matching game is not a substitute for a professional decision, and an arbitrary ranking does not become meaningful because it is interactive. Repeating a useful type is better than inventing a weak activity for variety.

### Career-relevant graphics are part of production

The AI must decide what the player needs to **see**, not only what they need to read. Build a graphic coverage map alongside the screen map. For each teaching or decision beat, record `graphic ID or none`, its purpose, what the player must notice and how it supports that beat. “None” is valid with a reason. Do not give every career the same workplace photograph and text cards, and do not add an arbitrary graphic quota.

Choose the artifact from the actual task:

| Work being taught | Reusable graphic family | Example content, not a fixed career template |
|---|---|---|
| Follow steps or branches | Flow / sequence | UX sign-up journey; service preparation; maintenance verification |
| Read a screen or compare versions | Interface / before-and-after | UX form and prototype states; dispatch panel; booking flow |
| Inspect spatial or physical evidence | Labelled diagram / plan | Building plan; equipment layout; room or station map |
| Read records, quantities or priorities | Document / table / chart | Research notes; fictional brief; inventory; schedule; finance evidence |
| Notice a visible condition or change | Scenario illustration / comparison | Food preparation state; customer setup; site condition |

These are reusable content families, not a claim that each already has a renderer in the app. Audit existing components first. Select only families that teach the career's real task. Do not copy a financial chart into nursing or put wireframes in every career.

For every selected graphic, the AI creates a specification before rendering:

```text
graphic ID; career/project ID; beat IDs; learning objective
family; what the player must notice; fictional/source status
canonical content data; labels; numbers/units; connections; state/version
related answer-key IDs; evidence supporting each key; distractor treatment
rendering route/component or asset file; allowed changes between versions
caption; alt text/text equivalent; phone layout; source/provenance
```

Use `artifact-master-prompt.txt` to fill this automatically. All task-critical labels, numbers, connections and answer logic come from **one canonical data record**. Derive the question's evidence and answer-key checks from that record; do not invent them separately in a generation prompt. Before/after states retain the same task and control every intentional difference. Do not reveal the key through an annotation unless that beat is teaching it.

**Rendering rules:**

1. Use existing native document, table, chat or generic components when they express the artifact. Render readable UI labels and quantitative evidence as native text/HTML/SVG generated from canonical data. This is designed visual content, not another paragraph under an illustration.
2. If no suitable renderer exists, create the smallest **shared, data-driven graphic primitive** and use the existing design tokens. Keep career facts and keys in data; no `career === X` layout branches. Validate it with two materially different career fixtures. This exception permits a reusable graphic renderer, never a new career-specific interaction/scoring system. Record the extension and its contract.
3. Use image generation for pictorial evidence, physical objects or illustration when useful. Keep task-critical text/numbers outside generated raster pixels. A workstation monitor may show a recognisable simplified version; provide the legible, authoritative artifact in the game UI when the player must inspect it.
4. Make every graphic usable at the actual phone and desktop sizes, with a text equivalent and keyboard-accessible controls if interactive. Never rely on colour alone, hover alone, invisible details, or a dialogue box hiding errors. Do not create a fake button in an illustration that looks like a working game control.
5. Verify visible content against the canonical record: labels, values, units, connections, ordering, version differences and keys. Test both useful and misleading evidence. Inspect the actual question and graphic together before handing over QA.

**Coverage gate:** the map must explain which decisions benefit from visual evidence, which do not, and how the career's actual deliverable becomes visible. For UX, include a coherent fictional sign-up flow, research evidence, wireframes and prototype changes where relevant. For a different career, derive equivalent work artifacts from its tasks. Generated graphics, their specs, sources, exact prompts, data and QA results travel with the game.

## 5. Build the level before art

Write a screen map with: beat ID, purpose, screen kind, visible cast, speaker, scene ID, concepts taught/used, question, alternatives, key/reason, skills, feedback, score status and source/assumption.

Use this flexible sequence:

1. Arrival and the concrete assignment.
2. What the role does; an example; an unscored check.
3. Mentor introduction just before the mentor matters.
4. Scored decision 1: an easy untimed win.
5. Several teach → example → practice → decision groups.
6. A mid-game review at a natural project milestone, after approximately half the scored decisions.
7. A project change, peer disagreement or reviewer challenge appropriate to this work.
8. An integrated final decision using earlier teaching.
9. An honest closing line, terminal review, and outcomes.

Aim for roughly 35–55 readable screens for the first project, not a fixed screen quota. Use exactly **ten scored decisions** in the standard Full level. Avoid padding with definitions, duplicate exposition or unnecessary character introductions. A multi-item block is still one scored decision.

For every scored decision, list the concepts it uses and a preceding beat that taught each one. An example illustrates a different case; it must not simply reveal the upcoming answer. The question must stand alone when its setup leaves the screen.

### Mid-game review is part of the authored level

Use the existing `card` / `variant: "act"` / `review` milestone (RN2-28, AMT and IB are references), not a new success screen implementation. Include its review intro, score count, conditional result and continuation. A passing result earns the success treatment; a failing result gets useful forward-looking feedback without confetti or a false success claim. It is unscored and must not add an eleventh decision.

Choose and document a threshold reachable at that point under the current score/recovery rules; do not reuse the final 85 threshold blindly when five Best decisions reach only 75 from a 50 start. Test pass, fail and continue. Offer Finish Later only when resume works; with `DEMO_START_FRESH`, omit that action or explicitly repair and test persistence within the requested scope. The initial UX draft omitted this milestone. The revised candidate implements UX1-MID after five decisions, with threshold 65.

### Copy and answer rules

- Plain language for students aged 13–14; a setup around 25 words, options usually around 10. Split dense explanations across deliberate screens.
- Exactly one Best for a one-pick decision. Wrong means unsupported or ineffective in the stated situation. Acceptable needs a real trade-off. Risky needs a real serious consequence; do not add one per level to satisfy a quota.
- Keep alternatives plausible and similar in length. Never make the answer obvious through word count, moral absurdity, repeated position or hidden visual styling.
- Each explanation teaches why **that option** fits or fails. Do not use the same generic explanation for every miss.
- No arbitrary leader preference presented as a fact. Where two answers are defensible, sharpen the constraints or accept both through a supported mechanic.
- Write a natural `planLineIfFailed` that completes the recovery sentence; exactly two registered skills per scored beat.
- Do not promise a real job, credential or promotion for a game score.

### Shared score and recovery contract

Use current `scoring.ts` and `SimulationPlayer.tsx`; do not fork them per career. Standard ten-decision levels start at 50, Best +5, Acceptable +2, Wrong −5 and Risky −6, clamped 0–100. Other decision counts scale in the engine; new standard levels use ten so no scaling is needed. The passing ending starts at 85. Tier headlines, answer locks, feedback timing and correction behaviour are engine-owned.

Default recovery: Wrong adds one strike, Risky two; the third strike opens the existing three-step plan, once per level. Two of three correct keeps the attempt alive. Recovery changes the baseline; later score cannot be predicted by simply adding the ten answers. The plan must use the new career's supervisor and examples, never IB fallback text.

Some approved IB/RN/AMT scripts intentionally use points overrides, no strikes, no repair or custom endings or different decision counts. Preserve those games. Do not copy a demo exception into a new career silently. If a new brief chooses an exception, record the reason in its content record and validation policy.

## 6. Complete scene art, no runtime sprites

Use `art-master-prompt.txt`. Keep script authority separate from art direction: art may improve staging but must not invent story events.

Before generation, save:

1. **Style reference:** one approved people-rendering reference and one environment-quality reference.
2. **Cast record:** permanent face/eye shapes, iris colours, skin, age, hair part/silhouette, build, clothing, accessories and canonical image per person. Distinct people, stable identities.
3. **Location/camera record:** room layout, window frames, furniture, fixed equipment and the entire view outside. Different windows may have different views, but each established view remains fixed.
4. **Scene plan:** script action, people, scene state, time, shared light direction, shot, required visible props, UI safe area and reuse/edit target.

Generate a **complete opaque scene** per necessary location/camera/state. Characters and surroundings are one finished image. Standing bodies continue below the waist; seated bodies belong to chairs and tables. Remove all UI during review so a cutoff cannot hide behind dialogue. Face chips are crops from these same images, not new portrait generations.

### Exact continuity: three different claims

| Claim | Enforcement |
|---|---|
| The same unchanged scene is pixel-identical across many beats | Reuse the same saved asset. Verify its file SHA and decoded pixel hash. Do not regenerate. |
| A reaction changes only the mouth/hand/expression | Edit the approved whole scene; record an allowed-change region or mask. Compare decoded pixels outside it. Exact mode requires **zero** changed protected pixels. Reject a failing candidate. |
| A new room/camera/time still depicts the same people and world | Use canonical identities and geography references; visually compare. This is continuity review, not a claim that all pixels are identical. New light necessarily changes pixels. |

A prompt alone cannot guarantee pixel equality. Do not use a favourable sample as proof that independent repeats are reliable. Do not call a seed a continuity guarantee. Provider/version/size/reference files and prompt text belong in the run record.

For locked areas, use an editing workflow that really preserves protected source pixels; if the available tool does not, keep the unmodified scene in the game and quarantine the candidate. Complete scene output does not mean the image must be re-generated for every line of dialogue.

For time changes, define what may change: light, sky brightness, practical fixtures and permitted scene states. Keep positions and geometry fixed. Do not use a simple dark filter as evidence that every physical shadow was relit. Use dawn/late-day god rays only where the window and source support them. Character and room light must agree.

### Asset budget

Count unique **location × camera × required state** combinations, not screens. The AI authors a shot coverage plan before generation: arrival, working action, conversation, visual evidence, escalation/change, mid-game milestone and closing, where those story moments exist. Vary camera, staging, activity and expression when the story changes, while preserving identities and location geography. Exact repeats are intentional only while the depicted state still fits. A named new camera need not be pixel-identical to another camera; it must agree with the room record.

Do not promise a fixed image count for every career. Coverage must be sufficient to show the work and its turning points; three rooms do not automatically mean three adequate images. The initial UX proof's three full scenes across 35 scene-bearing beats failed human coverage QA. The revised candidate has 15 planned compositions across 36 scene-bearing beats, with a coverage validator that rejects the old three-image manifest. RN's 18 routed compositions are a useful coverage comparison, not a universal quota. When an edit fails the pixel gate, report the missing variant and use an honest fallback; do not mark the coverage requirement passed merely because one file can repeat.

### Art acceptance

Reject a scene for: changed face/eyes/hair, same-face cast, comic/3D rendering, overdrawn hair, contradictory light, redesigned room/window view, floating waist, missing limbs, invalid object contact, dense fake text, obscured essential action or a broken phone crop. Luxury comes from appropriate architecture/materials/light, not detailed faces or irrelevant equipment.

Visual review is still required. A hash proves asset reuse, not anatomy, age accuracy or artistic quality.

## 7. Integrate as data

1. Add `<career>-level-1.ts` satisfying `Level`; no new interaction component.
2. Register the `Simulation` in `games.ts` with its exact catalogue ID/world and truthful built/upcoming ladder. Reuse art for its optional seven-card trailer; no statistics without sources.
3. Add `art/<career>.json`, register in `art/index.ts`, use `spriteStandard: "full-scene"`. Each location points to a complete image. **No character anchors**. Cast entries contain face chips and voice pitches; `default` sprites are optional for this format. Every non-review beat maps to a scene.
4. Keep camera crops stable per scene. Store source hashes, exact generation prompts and candidate/selected/approved status outside the runtime manifest.
5. Register career-specific recovery, intentional music state and any required Connect insight. If no licensed music exists, use the explicit silent list; do not borrow IB's soundtrack.
6. Express, if requested, removes only teaching screens; every scored decision and its meaning remains. Test that cut teaching is reachable through the existing tappable panels. Do not ship a cut that creates an unexplained test.
7. Use shared world tokens, typography, controls, sound and feedback. No new career palette or gameplay renderer. Work graphics follow the shared artifact extension contract above.

The shared full-scene mobile framing uses a shorter picture area so a landscape conversation keeps both faces above dialogue. It applies by manifest format, not career name; legacy sprite rooms retain their existing crop. Always verify each scene rather than treating this default as a universal safe area.

The old `art:extract` sprite pipeline is **not** a production step for this full-scene workflow. Do not turn the complete image back into cutouts. The existing full-scene player already renders this format.

## 8. Validation and release gates

Run from repository root:

```sh
node scripts/qa/validate-career.mjs ui-ux-designer
node scripts/qa/compare-protected-pixels.mjs base.png candidate.png edit-region.json
npx tsc --noEmit -p .
npx eslint <changed TypeScript files>
npm run tokens:check
npm run build
```

The generic validator checks IDs, ten decisions, progress, registered skills, nonempty payloads, one correct/Best where required, core-kit compliance, endings, teach/test ordering, scene routing, actual files, full-scene/no-anchor rules, voice/recovery entries and image opacity/hashes. The pixel comparator fails if dimensions change or any protected decoded pixel differs. These tools do not certify professional correctness or aesthetic quality.

### Runtime matrix

Test in the real game, not an image-only gallery:

- Start, How to Play, optional lesson, every question type actually used, correct/wrong feedback, error correction, mid-game review pass/fail/continue, all branches and final review.
- Graphic coverage, every artifact against canonical data, before/after changes, visual evidence and answer-key agreement; readable phone/desktop output and text alternatives. Test new shared graphic primitives with two different career fixtures.
- All-Best outcome; a non-passing outcome; recovery pass and failure if enabled; repair where enabled. Do not infer these solely from TypeScript compiling.
- Restart, reload/resume, switching careers, separate Full/Express saves if supplied.
- Desktop, tablet and phone widths; actual Windows/Chromebook QA before claiming those devices passed. Check required faces/props, readable options, no overflow and a complete image with dialogue hidden.
- Missing image/audio handling and intentional silence. Use the app's existing loading/error states.
- Regression smoke of IB, RN and aviation; no new bespoke fields or unintended changes to their data.

### Gates are separate

1. **Content:** correct keys and reasoning, sourced facts, honest role authority, AI source/key checks recorded; human authenticity QA status recorded, without requiring human authoring.
2. **Art:** canonical identity/geography, physical staging, time/light and crops reviewed; exactness claims backed by the right test.
3. **Engineering:** structural checks and build pass; runtime matrix completed with evidence.
4. **Release:** concrete diff, handoff WHY, known limitations, authorized destination. A local preview is not a production release.

**Current demo exception:** `DEMO_START_FRESH` in `progress.ts` deliberately disables resume in the live prototype. A reload starts fresh even though saves are written. Do not claim resume has passed or silently change existing games. Production release needs an explicit persistence decision and recovery-state tests. The earlier UX pilot recorded a phone CTA overlap from the Color control; current main makes that control desktop-only. Recheck the integrated build rather than carrying that old defect forward as a fact.

Do not let “all machine checks passed” imply all four gates passed. Include a status record for each: passed, failed, not run or pending review.

## 9. Test whether it scales

Use the **same build prompt and core engine** with a changed brief. A useful test set includes:

| Career family | Example assignment | Useful existing mechanics |
|---|---|---|
| Analytical | Support a recommendation with evidence | Document choice, flags, chain |
| Care/service | Notice a change and communicate priorities | Rank, pick, choice |
| Technical/trade | Verify work before sign-off | Flags, ordered checks, choice |
| Design/creative | Test a draft against a real task/brief | Bucket, rapid, chain |
| Field/hospitality | Prepare, adapt and hand over during service | Rank, pick, chat |

Vary employer, cast, environment, concepts and decisions. Keep component contracts unchanged. Record: new gameplay components added (target zero), shared graphic extensions and their two-career fixture checks, bespoke gameplay fields (zero), artifact coverage/key agreement, broken source facts (zero), teach-before-test gaps (zero), continuity failures, edit rejection rate, runtime defects, review effort and art calls. More careers tested gives stronger evidence; one UX pilot does not prove every career is solved.

Repeat generation independently as a stress test, not as a substitute for references. Test a new expression and time change from the same anchor. Quarantine drift and report the rate. A workflow that detects and rejects failure is more reliable than a prompt that hides failure behind cherry-picked results.

## 10. Required handoff package

Deliver the brief and source ledger; level plan; complete script/screen map; typed game data; answer rationale; teach/test trace; cast and geography records; complete scene images and same-scene face crops; generation prompts/run metadata; scene and graphic coverage maps; canonical artifact data/specs/rendered assets/text equivalents; scene-to-beat manifest/hashes; validation and browser evidence; unresolved issues and exact playable URL; release status/commit if published.

The authoring, scene art and artifact prompts travel with that package. Changing a reference, canonical cast design, model or prompt version starts a new candidate batch, not an invisible overwrite.

## 11. Enforced shot and viewpoint contract

Create `examples/<career-id>-coverage.json` before art production. Each required group records its purpose, scene ID, covered beats, visible cast, viewpoint, speaking target and eyeline. Each beat records its artifact ID or a reason no graphic is needed. The validator checks the plan against actual runtime routing and asset hashes; it rejects missing groups, accidental substitutions and duplicate files standing in for distinct required shots. It also verifies the midpoint exists after five decisions and its threshold is reachable. These are structural checks, not computer-vision proof of style or eye contact.

The player is the camera. For player-directed speech, the speaker faces the lens; no visible second character stands in for the player. Include peers only when the script calls for them. Observed-task and explicit NPC-to-NPC exchanges require a written reason. Select diverse roles before generating, then preserve each identity. Remove giant character-name splashes; ordinary dialogue labels carry the name and role.

## 12. Graphic design and game-action hierarchy

Use the actual medium: a wireframe is a neutral layout drawing, not a finished coloured form; a prototype has recognisable interface structure; research observations, quotes and uncertainties have separate compact cards. Use icons and connections to reduce repeated prose. Keep one concise teaching line and preserve what later decisions depend on.

The game owns the large primary CTA. Static artifact actions are non-focusable small outlined labels inside a bounded preview. A working prototype uses real local controls in its own inset canvas, explicit demo status and reset; no points, game advancement or external submission. Validate with keyboard, invalid input, success and reset. Motion clarifies entry or state changes and honours reduced motion. Do not autoplay a long loop.

Coverage follows the learning task and the story state. Remove a repeated graphic if it merely decorates another paragraph. Handover evidence before a test records that test as pending; a later release check records the actual blocker. UX v1.3 uses nine relevant graphic beats, rather than repeating seven records on 13 beats. This is a relevance decision, not a new quota.
